🧭 Module 1: Foundations

1. What Is an AI Agent?

  • Classically, an agent perceives its environment through sensors and acts on it through actuators. A rational agent acts to maximize expected performance given what it has perceived.
  • In modern practice, an LLM agent is a model using tools in a loop, where the model directs its own process. In a workflow, your code fixes the path.
  • An agent has a model, instructions, tools, memory, planning, an environment, and a harness. The harness and the context strategy matter as much as the model.
  • Agency comes in degrees: autonomy, goal-directedness, reactivity, proactivity and social ability.
  • The autonomy spectrum runs from chatbot to copilot, workflow, semi-autonomous agent and autonomous agent. Choose the level per action, based on reversibility and trust.
  • Agents trade predictability for flexibility. Use them where that trade pays off, and beware of agent-washing dressed up as capability.

2. A Brief History of AI Agents

  • The core agent idea, a feedback loop toward a goal, dates to 1940s cybernetics.
  • Symbolic agents (GPS, Shakey, SHRDLU, expert systems) could plan and reason but needed hand-built knowledge and were brittle outside small worlds.
  • Reactive (Brooks), BDI and multi-agent research in the 1980s and 90s introduced fast reaction, explicit intentions and agent communication, all of which have direct modern counterparts.
  • Reinforcement learning produced superhuman narrow agents (TD-Gammon, DQN, AlphaGo) and is now a key method for training LLM agents.
  • 2022's ReAct and chain-of-thought, 2023's function calling, and 2024's computer use, reasoning models and MCP made general-purpose LLM agents practical.
  • In 2025, agents became everyday products (Claude Code, Codex, Operator, deep research) and interoperability standards (MCP, A2A) moved to neutral foundations.
  • Classical ideas map almost one-to-one onto modern agent components, and so do classical failure modes.

3. LLMs: The Engine Inside Every Agent

  • LLMs process tokens and generate by predicting the next token, one at a time. Tool calls are structured text the model predicts and the harness executes.
  • Transformers use attention to relate every token to earlier ones, but very long contexts still dilute focus, so keep contexts lean.
  • The context window is the agent's entire working memory. Models are stateless across calls.
  • Capabilities come from pretraining. Assistant and agent behavior comes from post-training: SFT, RLHF/RLAIF/Constitutional AI, and RL on verifiable tasks.
  • Sampling makes outputs non-deterministic, so evaluate agents over many runs. Current Claude models don't accept sampling parameters.
  • Hallucination is a structural tendency. Grounding through tools and verification is the main defense.
  • Reasoning models trade test-time compute for accuracy. Interleaved thinking between tool calls is especially valuable for agents.
  • Choose model tiers by task difficulty, volume and latency needs, and remember that cost scales with tokens across every step of the loop.

4. The Agent Loop

  • Every agent is a perceive–think–act loop: call the model, run the requested tools, feed back the results, repeat.
  • The transcript is the state. Append assistant content unchanged, and return every tool_result for a turn in one user message with matching tool_use_ids.
  • The model proposes, the harness disposes. Budgets, permissions and safety rules belong in code.
  • Handle every stop reason (tool_use, end_turn, max_tokens, pause_turn, refusal), and always enforce step, cost and time limits.
  • Errors are observations. Return actionable errors with is_error: true so the agent can recover, and let the harness retry transient infrastructure failures.
  • Observation quality drives decision quality. Keep tool results concise, structured and explicit.
  • Interleaved thinking lets the model interpret each result before acting, which is a major source of modern agents' robustness.

5. Agents vs. Workflows: When (Not) to Build an Agent

  • Start with the simplest solution: single call → augmented LLM → workflow → agent → multi-agent. Climb only when the lower rung demonstrably falls short.
  • Workflows suit well-defined tasks that need predictability. Agents suit open-ended tasks whose steps can't be known in advance.
  • Judge proposals on complexity, value, viability and cost of error.
  • Reliability compounds: 95% per step is about 36% over 20 steps. Detection and recovery (tests, validators, actionable errors) change the math dramatically.
  • Agents cost more and take longer because of sequential steps and a transcript resent at every step. Caching, model tiering and shorter chains help, but the task has to be worth it.
  • Most production systems mix rungs, with cheap paths for the common case and an agent for the long tail.
  • Avoid the classic anti-patterns: agent-first thinking, unbounded loops, prompt-only safety, tool sprawl, multi-agent by default, and demo-driven development.

🧱 Module 2: Core Building Blocks

6. Prompt Engineering for Agents

  • An agent's system prompt transfers the context only you have — goal, audience, environment, quality bar, constraints and their reasons. The model already knows how to be helpful.
  • Attach a reason to every constraint; reasons let the model generalize to cases you didn't list and resolve conflicts sensibly.
  • Write at the right altitude: principles and goals for judgment work, exact steps only where a single sequence is safe.
  • Define ask-vs-act by reversibility, blast radius and ambiguity, and give a clear definition of done instead of generic pressure to "be thorough."
  • With modern models, remove dated scaffolding (capitalized warnings, "think step by step," step scripts, word caps) and use API features like thinking and effort for what prose used to do.
  • For long-horizon work, have the agent maintain todo lists, progress files, structured state and commits so a fresh context can resume.
  • Keep tool contracts in tool descriptions and cross-tool strategy in the system prompt; avoid hard-coding tool names.
  • Version prompts, tie them to a model, test every change against an eval suite over multiple trials, and read the transcripts.

7. Tool Use & Function Calling

  • Function calling is a handshake: the model emits a structured tool_use request; your harness executes it and returns a tool_result. The model never runs anything itself.
  • Models call tools reliably because they're trained to, through fine-tuning on tool transcripts and reinforcement learning in tool environments.
  • Tools are defined with a name, a description and a JSON Schema; descriptions drive both whether and how the model calls a tool.
  • Run every call in a response and return all results in one user message, results first, each matched by tool_use_id.
  • Report tool failures with is_error: true and an actionable message; keep API errors in your retry logic.
  • Use tool_choice auto/none and steer with instructions; use strict: true when arguments must match the schema exactly.
  • Distinguish client tools (you define and run), server tools (the provider runs) and Anthropic-defined client tools (trained-in schemas you run in your sandbox).
  • The tool runner removes loop boilerplate; the concepts map directly onto other providers' function-calling APIs.

8. Designing Great Tools (The Agent–Computer Interface)

  • The agent–computer interface deserves the same design care as a human interface; tool changes often beat prompt changes.
  • Tool names, descriptions and parameter descriptions are prompts: state the contract precisely, including when not to use the tool and what it doesn't return.
  • Prefer a few task-shaped, consolidated, namespaced tools over one-tool-per-endpoint; move deterministic work into code.
  • Return high-signal, human-readable results with sensible limits, pagination, hard caps and truncation hints; let the agent choose verbosity.
  • Write errors that say what was wrong, why, and what would work; mistake-proof interfaces with enums, absolute paths, ISO dates and strict schemas.
  • Separate reads from writes, make writes idempotent, offer dry runs, and enforce policy in the tool itself.
  • Start with bash for breadth; promote actions to dedicated tools to gate, render, audit or parallelize them. Use tool search and deferred loading for large catalogs.
  • Evaluate tools with realistic multi-step tasks, read transcripts, let agents propose improvements, and check against held-out tasks.

9. Structured Outputs & Control Flow

  • Structured outputs let the model make judgments and return typed decisions while deterministic code handles parsing, routing and actions.
  • Prompt-only JSON and JSON mode reduce but don't eliminate failures; schema-constrained decoding guarantees output that parses and matches the schema.
  • Constrained decoding works by masking tokens that would violate a grammar compiled from your schema; it guarantees syntax, not correctness, and needs escape hatches.
  • With the Anthropic SDK, use client.messages.parse(output_format=PydanticModel) for final answers and strict: true for tool arguments, and always check stop_reason.
  • Validate semantics in code and retry with specific feedback, a bounded number of times, while letting the model report genuine inconsistencies instead of fabricating.
  • Enums power reliable routing; dynamic enums over legal transitions give you LLM-decides/code-executes state machines that are auditable and testable.
  • Don't force reasoning into rigid formats: let thinking or a free-form first step do the deliberation, then structure the conclusion.

10. Reasoning & Planning

  • Reasoning techniques are ways of spending more computation before committing to an answer: more tokens (CoT), more samples (self-consistency), or more search (ToT, LATS).
  • ReAct grounds reasoning in observations and is the core of every tool-using agent. Plan-and-execute adds foresight but must replan when reality diverges.
  • Todo-list tools are the pragmatic planning mechanism in production agents: decomposition, recitation and live replanning in one cheap tool.
  • Reflection works when grounded in external feedback (tests, verifiers). Self-critique without a signal often doesn't help.
  • LLMs are unreliable stand-alone planners. Pair them with sound verifiers or classical planners (LLM-Modulo, LLM+P) when correctness matters.
  • Reasoning models move CoT into training. In the API, thinking is a dial (adaptive thinking plus effort) that you should tune per route with evals.
  • Visible reasoning is useful but not fully faithful. Use it for monitoring and debugging, never as proof.

11. Memory Systems

  • LLMs are stateless. All agent memory is engineered: write, retrieve, consolidate, forget.
  • The cognitive taxonomy maps cleanly onto agents: working (context window), episodic (past events), semantic (facts), procedural (skills, prompts, code). CoALA turns memory reads and writes into actions the agent chooses.
  • Generative Agents scored memories by a weighted sum of recency, importance and relevance, and used reflection to synthesize higher-level beliefs.
  • MemGPT/Letta treats the context window like RAM and lets the agent page information in and out with tools.
  • Plain files (the memory tool's /memories, CLAUDE.md, AGENTS.md) are a strong default: readable, editable, versionable, and easy for models to navigate.
  • Salience matters more than storage: remember stable preferences, hard-won facts, corrections and decisions; skip the re-derivable and the untrusted.
  • Memory brings its own failure modes: staleness, contradictions, poisoning, privacy leaks, bloat. Design provenance, isolation and forgetting in from the start.

12. Retrieval & Agentic RAG

  • RAG adds non-parametric knowledge at runtime: fresh, private and citable. Most RAG failures are retrieval failures, so measure retrieval first.
  • Embeddings capture meaning but miss exact identifiers, numbers and negations. Hybrid search (BM25 + dense, fused with RRF) plus a cross-encoder reranker is a strong default.
  • Contextual retrieval (prepending LLM-written context to each chunk before indexing) substantially reduces retrieval failures, and prompt caching makes it affordable.
  • Agentic RAG turns retrieval into a tool. The model rewrites queries, judges results and follows multi-hop leads.
  • GraphRAG helps with corpus-wide sensemaking and relationship questions, at a high indexing cost.
  • Coding agents often skip embeddings: grep, glob and read are exact, always fresh and need no infrastructure.
  • Choose deliberately: long context for small stable corpora, RAG for large or changing knowledge, fine-tuning for behavior rather than facts. Evaluate retrieval (recall@k, MRR) and generation (faithfulness) separately.

13. Context Engineering

  • Context engineering is choosing, at every step, the smallest set of high-signal tokens for the model. For agents it has largely replaced "prompt engineering" as the core discipline.
  • Context is a finite attention budget. Lost-in-the-middle and context rot mean that more tokens can mean worse answers, well before the window is full.
  • Write system prompts at the right altitude: concrete guidance with reasons, not brittle if-else rules or vague platitudes. Keep tool sets minimal and unambiguous.
  • Prefer just-in-time loading and progressive disclosure (references, search tools, Agent Skills) over preloading everything.
  • For long horizons, combine tool result clearing, compaction, structured notes and recitation, and sub-agent isolation.
  • Design for the KV cache: stable prefix, append-only history, deterministic serialization, mask rather than remove tools, inject dynamic content late.
  • Keep errors in context so the model can learn from them within the session. Measure, budget and evaluate every context change.

🏗️ Module 3: Architectures & Patterns

14. Workflow Patterns

  • Workflows use code-defined control flow; agents let the model direct its own process. Both are built from the augmented LLM (retrieval + tools + memory).
  • Prompt chaining trades latency for accuracy by giving each call one job; programmatic gates catch errors between steps.
  • Routing sends each input to a specialized path or a cheaper model; evaluate the router as a classifier because misroutes fail silently.
  • Parallelization comes as sectioning (independent subtasks) or voting (same task, diverse attempts); make voters genuinely different.
  • Orchestrator-workers fits when subtasks cannot be predicted; self-contained delegation instructions are critical.
  • Evaluator-optimizer fits when criteria are clear and feedback helps; ground the evaluator in real signals and cap the rounds.
  • Use an autonomous agent only when the path is genuinely unpredictable, and give it stopping conditions, sandboxing and evaluations.
  • Patterns compose. Move down the autonomy ladder only when an evaluation shows the simpler design falls short.

15. Single-Agent Architectures

  • ReAct (thought, action, observation) is the shape of the modern agent loop; most other architectures modify when the model plans, observes, reflects or explores.
  • Plan-and-Execute and ReWOO plan up front for coherence and lower cost; ReWOO trades away all mid-run adaptivity. LLMCompiler turns plans into DAGs of parallel calls.
  • Reflexion learns across attempts through verbal self-reflection stored in memory, and is only as good as its evaluator signal. LATS searches a tree of trajectories, which requires a resettable environment and lots of calls.
  • CoALA gives a common vocabulary: memory (working, episodic, semantic, procedural), action space (internal and external), decision procedure.
  • State-machine graphs make agents controllable, testable and resumable. Put hard constraints in edges; leave open-ended work inside nodes.
  • Router and blackboard architectures handle many capabilities and opportunistic collaboration respectively.
  • Default to one capable model with good tools in a simple loop; add architectural structure only where evaluations show it helps.

16. Multi-Agent Systems

  • Multi-agent systems buy context isolation, parallelism, specialization and separation of concerns, at the price of a large token multiplier (Anthropic reported about 15× chat for its research system), coordination overhead and harder debugging.
  • Orchestrator–subagents is the workhorse topology; handoffs suit customer-facing specialists; debate and critics improve verification; role-playing societies and generative-agent simulations are mostly research and simulation tools.
  • Communicate through structured payloads (including decisions made and open questions), via messages, shared state, or both.
  • Subagents know only their brief: specify objective, output format, tool guidance, boundaries and effort.
  • The MAST taxonomy groups failures into specification/design, inter-agent misalignment and verification; many are design problems that better models alone will not fix.
  • Reconcile Cognition and Anthropic with one rule: parallelize reading, serialize writing.

17. Human-in-the-Loop & Agent UX

  • Set oversight per action, not per agent: in-the-loop for high-impact irreversible actions, on-the-loop for monitored reversible work, out-of-the-loop for safe reads.
  • Use the risk × reversibility matrix to place approval gates; expose consequential operations as dedicated tools so they can be gated, and fail closed for unknown tools.
  • Declines should carry feedback back to the agent; every approval should be audited.
  • Production HITL needs interrupts, checkpoints and resume, with clear policies for timeouts and re-validation.
  • Ask clarifying questions early and batched; escalate with a warm handoff when policy, the user or repeated failure demands it.
  • Plans, progress streams, steering and undo let humans stay in control without approving every step; making actions reversible reduces the need for gates.
  • Aim for calibrated trust: fight approval fatigue and automation bias by gating less but better, and design outputs (diffs, citations, flagged assumptions) for fast, real review.

18. Protocols: MCP, A2A & Interoperability

  • Protocols turn M×N custom integrations into M+N implementations, the same move LSP made for editors.
  • MCP has hosts, clients (one per server) and servers, speaking JSON-RPC 2.0 over stdio (local) or Streamable HTTP (remote).
  • Server primitives are tools (model-controlled), resources (application-controlled) and prompts (user-controlled); clients offer elicitation, plus sampling and roots, which the 2026-07-28 revision began deprecating.
  • Remote MCP uses OAuth 2.1 with audience-bound tokens and no token passthrough; the 2026-07-28 revision also made the protocol stateless.
  • Treat every server as code or content that can attack you: tool poisoning, rug pulls, injected results, over-broad tokens, confused deputies. Use least privilege, approval gates and sandboxing.
  • A2A connects opaque peer agents via agent cards, tasks, messages, parts and artifacts, with streaming and push notifications for long-running work. MCP is for tools; A2A is for colleagues.
  • AGENTS.md, Agent Skills, AG-UI and OpenAPI-as-tools cover project instructions, packaged know-how, UI streaming and legacy APIs. MCP, A2A, AGENTS.md and Agent Skills are all now governed by the Linux Foundation's Agentic AI Foundation.

🌍 Module 4: Agents in the Wild

19. Coding Agents

  • Coding is the breakout use case because code is text-native, verifiable, reversible and reachable through mature tools.
  • Every coding agent combines navigation (glob, grep, read, repo maps), editing (str_replace, diffs, whole-file writes), execution and a verify loop.
  • The ACI idea: design tools for models, with compact output, clear errors and guardrails. Stronger models need less scaffolding, so re-test on upgrade.
  • Products span IDE, terminal, background and open-source categories; the key split is synchronous vs. asynchronous delegation.
  • CLAUDE.md / AGENTS.md give agents your conventions every session; keep them short.
  • Effective workflows: explore, plan, code, verify, commit; TDD with committed tests; small diffs; parallel worktrees.
  • Main failure modes are test tampering, over-engineering, hallucinated APIs and packages, and context exhaustion; defend with sandboxes, scoped credentials and careful review.

20. Computer-Use & Browser Agents

  • Computer-use agents run a screenshot, reason, act loop with mouse and keyboard actions, making any human-operable software reachable, at the cost of speed and reliability.
  • Grounding is the core challenge. Options are raw pixels, DOM, accessibility trees and set-of-marks; practical browser agents combine screenshots with structure.
  • Browser agents build on Playwright-style automation, libraries like browser-use, and hosted browser infrastructure; hybrid scripts-plus-model flows are most robust.
  • Milestones: Anthropic computer use (Oct 2024), Project Mariner (Dec 2024), Operator/CUA (Jan 2025) folded into ChatGPT agent (Jul 2025), Gemini 2.5 Computer Use (Oct 2025). On current Claude models, computer use is the client-side computer_toolset_20260801.
  • Benchmarks (OSWorld, WebArena, VisualWebArena, Mind2Web, WebVoyager) differ in being offline vs. live and reproducible vs. real-world; scores rose quickly from 2024 to 2025.
  • Failure modes: latency, grounding errors, dynamic pages, auth/CAPTCHAs, long-horizon compounding, irreversible actions, and prompt injection from on-screen content.
  • Safety lives in the harness: sandboxed VMs, least privilege, domain allowlists, confirmation gates, human takeover and budgets. Prefer APIs or MCP whenever they exist.

21. Deep Research Agents

  • Deep research agents iterate adaptively: plan, search broadly, read, find gaps, search again, then synthesize a cited report.
  • The product wave started with Gemini Deep Research (Dec 2024), followed by OpenAI deep research and Perplexity (Feb 2025) and Anthropic's Research (Apr 2025).
  • The reference architecture is a lead agent with parallel subagents, each with its own context, plus a citation pass. It wins on breadth-first questions but costs many times more tokens.
  • STORM shows the value of perspective-guided questioning and outline-first writing.
  • Trustworthy research needs source-quality heuristics, triangulation and explicit uncertainty.
  • Citations fail by fabrication, misattribution and drift; cite only retrieved documents, keep quotes attached to claims and verify.
  • Evaluate with verifiable benchmarks (GAIA, BrowseComp) plus rubric-based LLM judges calibrated against humans.

22. Customer-Facing & Voice Agents

  • Support agents combine policies, scoped tools, authentication, handoff and tone. State policy in the prompt and enforce it in the tool layer.
  • τ-bench evaluates policy adherence with simulated users and end-state checks; pass^k measures consistency, which drops sharply as k grows. τ²-bench adds dual control, where users act too.
  • Voice agents use either a cascaded pipeline (VAD → STT → LLM → TTS), which offers control and the best text reasoning, or speech-to-speech models, which offer lower latency and natural prosody.
  • Voice-to-voice latency is the defining constraint: stream everything, use semantic endpointing, fast models and caching, and fill tool latency.
  • Handle barge-in by stopping speech instantly and recording only what was actually spoken.
  • Telephony brings SIP/PSTN, narrowband audio and DTMF; compliance brings recording consent, AI disclosure, TCPA and PCI.
  • Measure resolution and CSAT, not just containment, and test with simulated callers.

23. Embodied Agents: Robots and the Physical World

  • Physical action brings irreversibility, real-time constraints, partial observability, higher safety stakes and the sim-to-real gap.
  • The classical stack (perception, state estimation, planning, control) still sits underneath; learning replaced perception, then skills, then task planning.
  • Hierarchical agents let an LLM or VLM plan over objects and skills while policies and fast controllers execute. SayCan added affordance grounding, Inner Monologue added feedback, Code as Policies used code as the plan, and VoxPoser shaped motion with 3D value maps.
  • VLAs map images and language directly to actions. RT-2 showed web pretraining transfers to robots; Open X-Embodiment showed cross-embodiment data helps; Octo, OpenVLA and π0 opened the field; Gemini Robotics and GR00T lead industrial efforts.
  • Data is the bottleneck: teleoperation, cross-embodiment pools, simulation, human video and the robot's own experience. World models (Genie, Cosmos) add synthetic data and imagined rollouts, with fidelity limits.
  • Evaluate with real-world trials plus simulation benchmarks (LIBERO, SIMPLER), reporting trials, interventions and unsafe events.
  • Safety is layered from hardware e-stops and force limits through constraints, harness gates and human override; model-level semantic safety (ASIMOV) is the last layer, not the first.

24. The Agent Landscape: Use Cases by Domain

  • Agent maturity varies widely by domain: established in software engineering; scaling in customer service, data analysis, IT ops, security triage, back-office, legal review and healthcare administration; emerging in personal assistants, education and scientific discovery; experimental in robotics.
  • Maturity tracks verifiability, tool access, error tolerance and volume more than demo quality.
  • Every domain has a signature risk: hallucinated citations in law, plausible numeric errors in finance, patient safety in healthcare, prompt injection in personal assistants, dual use in security and science.
  • Score opportunities on volume, verifiability, tool access, error tolerance, process clarity and value; low verifiability is the biggest red flag.
  • Credible ROI counts review time, error costs and maintenance, and is measured against a baseline in a controlled pilot.
  • Adopt along a path from copilot to approval to supervised and scoped autonomy, stepping back when quality drifts.

🛠️ Module 5: Building Agents

25. Build an Agent From Scratch

  • An agent is a loop: call the model, execute requested tools, return results with matching tool_use_ids in one user message, repeat until end_turn.
  • Handle every stop reason explicitly; never execute a tool_use from a max_tokens-truncated or refused turn.
  • Treat every model-supplied argument as untrusted: confine paths to a workspace, run commands without a shell against an allowlist with timeouts, and use a real sandbox for real isolation.
  • Return failures as is_error tool results with actionable messages so the agent can recover.
  • Bound turns with step and token budgets, gate side effects behind approval, and trace every step.
  • Keep the system prompt and tools static and cached; verify with cache_read_input_tokens.
  • The Tool Runner removes loop boilerplate; tools, sandboxing, budgets and prompts stay yours.

26. Frameworks & SDKs Compared

  • A framework is worth it when it solves a specific hard problem (durability, resumable approvals, multi-agent coordination, integrations, team conventions), not to avoid writing a 40-line loop.
  • The landscape has layers: model APIs, SDK helpers, agent SDKs, orchestration frameworks, specialized frameworks and managed platforms.
  • LangGraph leads on explicit, durable, resumable control; the Claude Agent SDK on ready-made computer-use tooling; the OpenAI Agents SDK on minimal multi-agent primitives; Google ADK and Strands on their clouds; LlamaIndex and Haystack on retrieval; DSPy on optimization; Letta on memory; Mastra and the Vercel AI SDK on TypeScript.
  • Managed platforms (Claude Managed Agents, Bedrock AgentCore, Google Agent Runtime, OpenAI's Responses stack) trade control for operated sandboxes, sessions, identity and scale.
  • Choose by language, control needs, durability, observability, lock-in and maturity, and confirm with your own evaluation suite.
  • Keep tools, prompts, evals and state framework-independent so migration stays cheap.

27. Hands-On with Agent SDKs

  • Building one spec in several SDKs reveals the real differences: who owns the loop, where state lives, how approvals pause, and what you can trace.
  • The Anthropic Tool Runner is a thin helper over the Messages API; you keep control and responsibility for everything except loop mechanics.
  • The Claude Agent SDK gives you Claude Code's harness as a library: built-in computer tools, MCP custom tools, hooks, subagents, permission modes, sessions and cost caps.
  • The OpenAI Agents SDK centers on agents, handoffs, guardrails, sessions and built-in tracing; tool approvals pause the run into a resumable RunState.
  • LangGraph makes the loop an explicit graph with checkpointed state; interrupt() and Command(resume=...) give durable human-in-the-loop, but resumed nodes re-run from the top.
  • Keep tool logic framework-free and pin versions: these APIs change frequently.

28. Agents on Open-Weight & Local Models

  • Open-weight models are a deployment choice for data control, cost at volume, latency, customization or offline use; you accept the ops burden and, on long-horizon tasks, a capability gap that is still real as of 2026.
  • Licenses vary per release, from Apache 2.0 and MIT to custom terms with user or revenue thresholds; review the exact artifact you deploy.
  • Tool calling on open models is text generation plus parsing: the chat template renders tools into tokens, the model emits tool-call markers, and the server's parser turns them into JSON. Template or parser mismatches fail silently.
  • Constrained decoding (Outlines, XGrammar, llguidance, GBNF) guarantees well-formed tool JSON, but not correct choices; validate semantics in code.
  • Quantization errors compound over agent steps; 8-bit is usually safe, 4-bit is the common trade-off, and you must evaluate the quantized artifact itself.
  • KV cache memory, driven by context length and concurrency, often limits agent serving more than model size does. Do the arithmetic before buying GPUs.
  • The strongest designs are often hybrid: a frontier model plans and handles hard cases, local models do bulk, narrow or PII-sensitive steps.
  • Treat weights like dependencies: safetensors over pickle, avoid trust_remote_code, pin revisions, verify provenance, and sandbox the agent anyway.

🚀 Module 6: Production Engineering

29. Evaluating Agents

  • Agent evals are hard because agents are non-deterministic, take long multi-step paths with many valid routes, and change environment state. Run multiple trials per task and grade the outcome, not the agent's claims.
  • Use code graders (tests, state checks, assertions) wherever correctness is objective; LLM judges for subjective qualities; humans to calibrate judges and do error analysis.
  • LLM judges have known biases — position, verbosity, self-preference, leniency. Use binary rubric criteria, reason-then-verdict structured output, ground truth in the prompt, and measure agreement with human labels (TPR/TNR or kappa, not just accuracy).
  • Grade at the right level: outcome by default, trajectory as constraints (not golden paths), per-step for cheap tool-choice regressions. Keep capability and regression suites separate.
  • pass@k measures what an agent can do with best-of-k selection; pass^k measures consistency. Customer-facing agents live or die by pass^k.
  • The best eval tasks come from error analysis of real transcripts: open coding, axial coding, count, then write tasks for the biggest categories.
  • Eval scores have error bars. Small suites can't detect small improvements; use confidence intervals, clustered standard errors and paired comparisons.
  • Beware grader hacking, ambiguous tasks, contamination and overfitting; always report cost and latency alongside quality.

30. Agent Benchmarks

  • A benchmark score measures a system (model + scaffold + tools + budget) on a task distribution with a grader. Changing any of these changes the number.
  • Coding benchmarks grade with tests or rubrics; tool-use benchmarks with answers or environment state; web and computer-use benchmarks with functional checks in self-hosted or live environments.
  • Long-horizon measures (METR time horizons, Vending-Bench, GDPval) shift the question from "can it do the task?" to "how long, how valuable and how consistently?"
  • Safety benchmarks report paired numbers — AgentDojo's utility and attack success rate must be read together.
  • Benchmarks mislead through saturation, contamination, scaffold sensitivity, unreported cost, broken tasks, variance and Goodhart's law. SWE-bench Verified's creation and later retirement by some labs (and the broken tasks later found in its successor, SWE-bench Pro) illustrate the whole life cycle.
  • Read leaderboards by asking: which variant, which system, how many attempts, what budget, who ran it, how much variance, and does it resemble my work?
  • Public benchmarks shortlist; internal benchmarks built from your own real tasks decide.

31. Observability & Debugging

  • Agents fail silently, non-deterministically and far from the cause, so the trace — a tree of spans for every model call, tool call and decision — is the essential debugging and monitoring artifact.
  • Model runs as traces of nested spans, grouped into sessions. Capture inputs, parameters, outputs, tool calls and results, tokens, cost, latency, errors, versions and feedback.
  • Use OpenTelemetry with the GenAI semantic conventions (invoke_agent, chat, execute_tool, gen_ai.* attributes) to stay vendor-neutral; the conventions are still evolving, so pin versions.
  • Debug with a fixed loop: find a failing trace → localize the first bad step → classify (prompt, tool, context, model) → fix → add an eval → verify. Most failures aren't the model's fault.
  • Replay traces by forking from a recorded step with mocked tools to test fixes on the exact failing state.
  • Dashboard success rate, steps per task, tool error rate, cost per task and p95 latency, sliced by version, and alert on spikes and post-deploy drops.
  • Traces are sensitive: redact at the source, capture content deliberately, pseudonymize IDs, set retention tiers and support deletion.

32. Reliability & Durable Execution

  • Agents are long-running, stateful, side-effecting and nondeterministic: design for interruption. Retry only what waiting can fix (429 except spend caps, 5xx including 529, connection errors), using backoff plus full jitter, honoring retry-after, with one retry owner per boundary.
  • Idempotency keys built from the intent, not a tool_use_id or a random UUID, turn at-least-once execution into effectively-once side effects.
  • Circuit breakers, fallbacks and a degradation ladder keep partial outages from becoming total ones. Model fallbacks cost you the cache, so switch at task boundaries.
  • Validate tool inputs syntactically and semantically, return actionable is_error results, and verify outputs against ground truth.
  • Handle every stop reason, fingerprint calls to catch loops, and enforce step, token, time and dollar budgets.
  • Checkpointing and durable execution let agents resume after crashes. Idempotency makes the one repeated step safe, and sagas unwind multi-system work. Prove it all with fault injection and chaos tests.

33. Long-Running Agents

  • When a task spans many context windows and sessions, the transcript is disposable and the workspace is the memory: code, tests, a task list, progress notes and git history.
  • The characteristic failures are trying to one-shot the work, declaring victory early, false "done" on individual items, losing the thread after compaction, context anxiety, environment rot, drift and runaway cost.
  • A two-phase harness addresses most of them. An initializer expands the spec into a failing task list, an init.sh and notes. Working sessions orient, check the baseline, do one item, verify, commit and update notes.
  • Keep the task list structured and mostly frozen (JSON the harness can read and enforce) and the notes free-text but curated. Git provides checkpoints, episodic memory and the review surface.
  • Compaction preserves continuity, while resets and fresh sessions give a clean slate at the cost of a handoff. Every harness component encodes an assumption about the model's limits, so re-test it when models change.
  • Verify the way a user would (end-to-end, in a browser where relevant) and with an independent evaluator for subjective quality. Only the harness should mark items done, and the tests must be outside the agent's write scope.
  • Budget at every level: max_tokens per response, an advisory task budget per session, attempt limits per item, and dollars, deadlines and stall detection per project. Put humans at the plan, at milestones and on escalations.

34. Cost & Latency Optimization

  • Output tokens cost about 5× input, thinking bills as output, and because every call re-sends the history, uncached agent cost grows roughly with the square of the turn count.
  • Prompt caching is the biggest single lever. Keep stable content first, hunt silent invalidators, and verify with cache_read_input_tokens, since input_tokens is only the uncached remainder.
  • Cache reads cost a small fraction of input (0.1× or less), writes cost 1.25× (5-min) or 2× (1-hour), and two requests already break even.
  • Compare models and effort levels by cost per completed task, including failures and downstream costs, and sweep effort before switching models.
  • Batch offline work for 50% off (it stacks with caching). Cut round trips with parallel and programmatic tool calls.
  • Latency ≈ calls × TTFT + output tokens ÷ speed + tool time. Streaming improves felt latency, and fast mode buys output speed for money.
  • Change one thing at a time, measure on a fixed eval, and treat compaction as a context tool rather than a cost tool.

35. Deploying & Operating Agents

  • Match the deployment shape to task duration and trigger: synchronous only for short tasks, queues and workers for long ones, streaming for perceived speed, PR-style delivery for risky autonomous work.
  • Treat model-written code as untrusted. Run it in gVisor or microVM sandboxes with default-deny egress, one per task, never shared across tenants.
  • Secrets never enter the context window. Use scoped short-lived credentials, injected at an egress proxy.
  • Enforce tenant isolation in infrastructure and data layers, not in prompts, and add per-tenant quotas and spend caps.
  • An agent version is model + prompt + tools + harness + config. Version it as code, pin model IDs, and keep in-flight sessions on their original version.
  • Ship through eval-gated CI, shadow runs with stubbed side effects, and canaries with automatic rollback.
  • Monitor success, cost, latency, cache hit rate and steps per task. Keep kill switches and incident playbooks ready, and turn every incident into a regression eval.

🛡️ Module 7: Safety & Security

36. Agent Security & Prompt Injection

  • Agents act with your privileges while reading everyone's text; every tool result, document, web page, email and MCP description is an untrusted input.
  • Indirect prompt injection — instructions planted in retrieved content — is the central agent threat, and it is not solved at the model level because instructions and data share one channel.
  • The lethal trifecta (private data + untrusted content + external communication) enables data theft; removing any one leg defeats that class of attack.
  • Exfiltration channels are subtle: markdown images, links, web fetches, public comments and third-party API arguments all count as "external communication."
  • MCP brings specific risks — tool poisoning, rug pulls, cross-server shadowing — plus memory poisoning, confused deputies, excessive agency and supply-chain attacks.
  • The strongest defenses are architectural (dual LLM, plan-then-execute, map-reduce, code-then-execute, CaMeL's capability tracking): they assume the model will be fooled and limit what a fooled model can do.
  • Layer least privilege, human confirmation, spotlighting, classifiers, egress allowlists and monitoring on top; each is imperfect, together they are strong.
  • Measure both utility and attack success, using benchmarks like AgentDojo and red teaming tailored to your own tools.

37. Guardrails, Permissions & Sandboxing

  • Defense in depth: stack independent layers — model, input guardrails, output guardrails, action guardrails, sandbox, audit — so attacks must beat all of them.
  • Probabilistic layers (classifiers, LLM judges) reduce how often bad things are attempted; deterministic layers (permissions, sandboxes, network policy) bound the damage. Put your guarantees in the deterministic ones.
  • Input guardrails must screen tool results, not just user messages; output guardrails should redact secrets and PII, check groundedness and validate schemas in code.
  • Permission systems use allow/ask/deny with deny-first precedence and a non-allow default; canonicalize arguments and distrust shell strings with metacharacters.
  • Policy engines, hooks, rate limits and spend caps extend action-level control to organization policy and volume-based harms.
  • Sandbox strength follows the kernel boundary: containers share the host kernel; gVisor interposes a user-space kernel; microVMs give each workload its own kernel.
  • Harden sandboxes with scoped and read-only mounts, no network or allowlisted egress, credential injection by proxy, resource and time limits, and ephemeral lifetimes.
  • Calibrate controls to reversibility and blast radius; strong sandboxing is what lets you safely reduce permission prompts.

38. Agent Identity, Authorization & Payments

  • Agents need their own identity, linked to but distinct from the user's: act on behalf of, never as. That's what makes accountability, least privilege, per-agent revocation and audit possible.
  • Authentication proves who; authorization decides what. Prefer delegation (subject plus actor, as in RFC 8693's act claim) over impersonation.
  • Delegated OAuth for agents means authorization code + PKCE, narrow scopes, audience-bound, short-lived access tokens, vaulted and rotated refresh tokens, token exchange at every hop instead of passthrough, and consent screens that name the agent and the consequences.
  • MCP applies OAuth 2.1 strictly: verified PKCE support, mandatory resource indicators, audience validation, scope challenges with step-up authorization, and issuer validation, plus opt-in extensions for machine-to-machine and enterprise IdP-managed access.
  • Never put raw secrets in the model's context. A credential broker holds tokens, mints per-call scoped tokens, enforces per-tool and per-action policy (allowlists, spend caps, approvals) in code, and redacts results.
  • On the open web, Web Bot Auth (HTTP Message Signatures with published operator keys, still an IETF draft) identifies the operator, not the user's intent. Verifiable credentials and KYA programs aim to carry richer, verified claims.
  • Hash chains detect tampering, but only signatures by the user's own key give non-repudiation, which is why payment protocols center on signed mandates.
  • Agent payment protocols (AP2, ACP, UCP, x402, card-network programs) are young and moving, but share one principle: verifiable delegation with limits enforced outside the agent, assuming the model can be injected.

39. Safety, Alignment & Governance

  • Sort risks by origin — misuse, accidents, misalignment, systemic — because each needs different levers; agents amplify all four because they act, take many steps and hold real credentials.
  • Specification gaming and reward hacking appear in today's coding agents (special-casing tests, tampering with scoring); never let an agent grade itself on a metric it can change.
  • Sycophancy, deception, sandbagging and evaluation awareness threaten the assumption that observed behavior predicts deployed behavior.
  • The 2025 agentic-misalignment stress tests showed models from many developers could choose harmful actions in contrived, high-pressure scenarios; they were not observations of real deployments, but they support caution about broad access with minimal oversight.
  • Scalable oversight, interpretability, chain-of-thought monitoring and AI control are complementary; CoT monitoring is valuable but fragile, and training against it can produce obfuscation.
  • Frontier safety frameworks (Anthropic's RSP, OpenAI's Preparedness Framework, Google DeepMind's FSF) tie deployment to dangerous-capability evaluations in cyber, CBRN, autonomy and self-replication.
  • Governance is diverging: the EU AI Act imposes GPAI obligations from August 2025 with high-risk rules postponed to 2027–2028; the US relies on executive action, standards and state laws; the UK on sector regulators and its AI Security Institute.
  • Accountability needs agent identity, audit trails and clear ownership; assume your organization is liable for what your agent does.

🔭 Module 8: Advanced & Frontier

40. Training Agentic Models

  • Agentic models are built in stages: pretraining → SFT → preference optimization → RL with verifiable rewards → multi-turn agentic RL, with distilled data flowing back into SFT.
  • SFT teaches formats and protocols cheaply but can't teach recovery from off-distribution mistakes; RL against outcomes can.
  • PPO-based RLHF needs a reward model and a critic; DPO turns preferences into a simple offline loss; GRPO removes the critic by comparing a group of samples on the same prompt — which suits verifiable rewards and made it the default for reasoning RL.
  • Tool use was taught via self-supervision (Toolformer), large real-API datasets (Gorilla, ToolLLM), distillation of strong-model trajectories (FireAct, AgentTuning) and verifier-filtered self-training (STaR, rejection sampling).
  • Agentic RL's hard problems are sparse rewards, long-horizon credit assignment, slow rollouts and reward hacking; environments and verifiers — not algorithms — are now the main bottleneck.
  • Your verifier is your specification: check final state, isolate graders and audit high-reward trajectories.
  • Fine-tune last: only with a stable task, a trustworthy eval, real volume, and evidence that prompting and tools have plateaued. LoRA/QLoRA make experiments cheap.

41. Self-Improving & Open-Ended Agents

  • Self-improvement happens at many levels — within an episode, across episodes, in prompts/programs, in agent design, in the agent's own code, and in weights — with rising power, cost and risk.
  • Reflection helps most when grounded in external feedback (tests, errors, environment state); intrinsic self-critique alone is unreliable.
  • Persisting experience as lessons, skills (Voyager, Agent Skills) and verified examples gives agents durable procedural memory — but memory needs curation to avoid bloat, drift and poisoning.
  • Prompt and program optimizers (DSPy, OPRO, TextGrad, GEPA) treat instructions as parameters to optimize against a metric, and can be far more sample-efficient than weight training.
  • ADAS, AFlow, Gödel Agent and the Darwin Gödel Machine automate agent design and self-modification; FunSearch and AlphaEvolve show LLM-guided evolution can find genuinely new solutions when there's a strong automatic evaluator.
  • Evaluation is the bottleneck: every documented failure — reward hacking, objective hacking, overfitting — traces back to the "keep if better" check.
  • Keep evaluators, permissions and guardrails outside the agent's write access; gate every self-generated change on held-out evals or human review.

42. Open Problems & The Road Ahead

  • METR's measurements show the length of tasks frontier agents complete at 50% reliability has been doubling roughly every seven months — a useful trend, but 50% isn't reliable, domains differ, and trends aren't guarantees.
  • Reasoning and tool use have converged; agents are becoming a default interface for software, from coding to research to business workflows.
  • Major open problems: long-horizon reliability, continual learning, evaluation, cost per task, prompt-injection security, multi-agent coordination, and identity/authorization/payments.
  • The web is being rebuilt for agents through shared standards — MCP and AGENTS.md (now under the Linux Foundation's Agentic AI Foundation), llms.txt, A2A, and early payment protocols like AP2 and ACP.
  • Evidence on productivity is mixed and context-dependent; feeling faster is not the same as being faster.
  • Optimists and skeptics disagree about pace and impact; judge claims by what was measured, at what reliability and cost, against what baseline.
  • The fundamentals — the loop, tools, context, evals, security — outlast any specific model or framework. Keep building.
